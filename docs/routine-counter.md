# 演技構成(A案/B案)の完走本数カウンター 仕様と決定の経緯

最終更新: 2026-09-09 / 対象: index.html（本番 https://vanwhist.github.io/hannan-trampoline-log/ ）

## なぜ作ったか

城瑛斗（中1）が近畿ジュニア(10/4)に向けて演技構成を2つ作る。

- A案 … これで行きたい版
- B案 … 調子が上がらなかったとき版

「締切日までにA案を◯本完走できたらA案でいく、できなければB案」という切り替え基準を、
大会前の時点で先に決めておく運用にした。**その「何本完走したか」を数えるのがこの機能。**

判断を大会当日にしないための仕組みなので、アプリは**数を出すだけで、判定はしない**。

## 数え方

| 項目 | 決めたこと |
|---|---|
| 数える対象 | 結果が「完走」の実施記録のみ |
| 開始日 | **そのルーティーンをアプリに登録した日**（favorite の createdAt / JST）。それより前の記録は数えない |
| 締切日 | 設定で変更可（未設定なら締切なしで数え続ける）。締切を過ぎた記録は数に入らない |
| 積み上げ方 | **通算**。中断してもリセットしない。目標に達しても止めずに増え続ける |
| 部分ルーティン | ルーティーンごとに独立して数える。A案の本数に混ざらない |

**部分ルーティン（頭から5本、つなぎ3本など）は、ルーティーンとして別途登録すればそのまま使える。**
構成ごとに別々の数字が出るので、「A案の完走本数」に部分の完走が混ざることは構造上ない。

## 結果の言葉を「成功/失敗」から「完走/中断」に変えた

- ヨレても最後まで跳び切ったら**完走**。途中で止めたら**中断**。
- 測りたいのは「本番で構成が最後まで持つか」であって演技の質ではない。質はコーチが別に見る。
- 「失敗」は人への評価に近い言葉、「中断」は起きたことの記述。跳んだ直後に本人が自分の演技の質を
  自己評価する構造を作らないため、言葉のほうを事実の記述に寄せた。
- **保存する値は従来どおり `success` / `fail`。** 表示ラベルだけを変えているので過去データと互換。

### 採用しなかった案
- **3択（完走 / 中断 / 完走したが内容が悪い）** … 本人に演技の質の自己評価をさせることになる。
  また「あれは完走に入れていいのか」という解釈の余地が生まれ、
  「争いようのない事実である」というこの基準の価値そのものを壊すため不採用。
- **単発モードも完走/中断に統一** … 不採用。単発は「技が決まったかどうか」そのものなので
  「成功/失敗」が事実として正確。言い換えを広げると「ここは触れてはいけない話題だ」という
  メッセージが伝わって逆効果になる（本人は120本を淡々と入力して成功率64%→86%まで上げている）。

## 表示の決めごと

- **「A案 完走 7本」と数だけ。分数（7/10本）にしない。**
  分数は「残り3本」を意味し、締切が近づくほど跳ぶ直前に「届くか届かないか」が乗る。
  実行の直前に予定外の判断が乗ると演技が崩れるという実例があるため、その構造を練習に持ち込まない。
  数だけなら悪い日は増えないだけで、減らない。
- 置き場所は**保存ボタンの直下（記録タブ）**と**ダッシュボードの「構成ごとの完走本数」カード**。
  跳んで保存した直後に、目を動かさずに数が増えたのが見える位置。
- **目標本数は記録タブに出さない。** ダッシュボードの設定画面にだけ置く。
- **警告を出さない。** 赤字・「あと◯日」・「このままでは未達」の類は一切なし。
  焦らせると、合わない日に無理に本数を稼ごうとする。うまくいかない練習を自分の判断で
  切り上げられることを我々は正しい判断として評価しているので、アプリがそれと逆に働かないようにする。
- 締切を過ぎたら「完走」→「**期間内完走**」に変わって数が止まるだけ。
  **達成/未達の判定文はアプリに出させない。**

## 締切日と目標本数の保存場所

**localStorage（その端末のブラウザ）に保存する。Apps Script／スプレッドシートには持たせない。**
キー: `tramp.routineGoals.v1`

サーバに載せると、保護者の端末からも本人の知らないところで本数を確認できる状態になる。
それは避けると決めた「大人の管理ツール」そのもの。
ローカルなら、数字を見るには本人の画面を一緒に見るしかない。
締切日に本人が自分のスマホを見せて確認する、という形が自然に強制される。
**制約ではなく、仕様としてこちらを選んでいる。**

### 採用しなかった案
- **Apps Script に設定の保存先を追加して両端末で同期** … 上記の理由で不採用。

### ブラウザのデータが消えた／機種変更したとき（実測で確認済み）
- **完走本数のカウント表示は壊れない。** 数え上げの元データはスプレッドシート側にあるため。
- **締切日の打ち切りだけが効かなくなる**（締切後の記録も数に入り続ける）。表示は「期間内完走」→「完走」に戻る。
- **締切日を入れ直せば、まったく同じ数字に戻る。**
- 同時に、選手の選択記憶と表示高速化用キャッシュも消える（実害なし）。
- 対策として、**本人が決めた期限と本数は紙にも書かせる**（A案・B案の技構成と同じ紙に並べる）。

## 練習運用（アプリ側の前提）

**通しは、その日のいちばん最初に1本やる。**
自由に決めさせると単発ばかりになって通しに到達しないため。最初にやれば、
そこで抜けた技がその日の練習内容になる。これにより通しの記録が毎回発生する。
なお1本は下限であって上限ではない。

## 実装メモ

- `routineRunStats(fav, athleteId)` … 完走本数・開始日・締切日・締切済みかを返す
- `routineCounterLine(fav, athleteId)` … 記録タブに出す1行（数だけ）
- `renderRoutineCounterCard(athleteId)` … ダッシュボードのカード
- `renderRoutineGoalModal()` / `setRoutineGoal(favId, key, value)` … 締切日・目標本数の設定
- `routineStartDate(fav)` … 登録日(JST)。`createdAt + 9h` を ISO 日付に切る
- **実施記録は favoriteId を持たず routineName（名前）で保存されている。**
  そのため集計もルーティーン名で引き当てている。
  **ルーティーンを改名すると、過去の記録は旧名のままなので集計から外れる。**
  A案・B案は改名しない前提。改名が必要になったら、この点を先に検討すること。
- 同じ理由で、`emptyRoutineExecDraft(athleteId)` は
  `recentFavoriteIdFor(athleteId)`（直近の実施記録の名前→FAVORITES を逆引き）で初期選択を決めている。

## 入力の軽さ（この機能で守っていること）

記録は本人が体育館で跳んだ直後に入れる。**1本ぶんが数タップで終わることが最優先。**
保存後もルーティーンの選択が残るので、2本目以降は「完走/中断」1タップ＋保存1タップの計2タップ。
（以前は保存のたびに選択が消え、毎回プルダウンから選び直しで4タップ必要だった）
